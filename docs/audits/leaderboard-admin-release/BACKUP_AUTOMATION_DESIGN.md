### Zero-cost limits that remain unresolved

This does **not** meet an immutable or upload-only security boundary. A personal My Drive folder has no create-only role: a folder writer can add, edit, and delete files. `drive.file` narrows the app's per-file access, but files it creates remain modifiable/deletable by that OAuth principal. Drive's read-only content restriction is mutable and explicitly is not an immutable record. Therefore a compromised uploader refresh token or job could delete its recovery points. A separate owner verifier can detect missing/changed files, but cannot prevent that deletion. These Google Drive limitations are documented at [Drive roles](https://developers.google.com/workspace/drive/api/guides/ref-roles) and [content restrictions](https://developers.google.com/workspace/drive/api/guides/content-restrictions).

The uploader must never call update, delete, permission, or trash operations; use random/date-stamped names and a pre-create duplicate check. If an upload times out after a possible success, stop and reconcile by backup ID before retrying. These are application safeguards, **not** provider-enforced immutability. Do not claim the result is production recovery-ready until the owner accepts this residual risk or provides an already-paid/available storage system with enforceable append-only controls. No such zero-cost immutable Drive permission was found.

## Capacity guard

Personal Google accounts have up to 15 GB shared among Drive, Gmail, Photos, and other Google services; the actual limit and free space are account-specific and unknown here. Before each upload, call Drive `about.get` for `storageQuota(limit,usage)`, get the exact encrypted package size from disk, and stop unless:

`usage + packageBytes + ownerApprovedReserveBytes <= limit`

Missing/invalid quota fields, no configured positive reserve, a quota overrun, or API failure is a hard stop. Never delete files automatically to make space. Check again immediately before every package file, because usage can change between calls. The owner's approved candidate policy is one weekly package and four retained successful recovery points. Estimate storage as `4 × current complete encrypted package size` plus the owner-approved reserve; the historical ~1.26 MB package estimate is stale and excludes private Storage bodies, manifests, and growth. Private object bodies may dominate the total. The job must measure actual bytes each run and stop before quota exhaustion. Google documents the account's shared quota at [Google storage limits](https://support.google.com/drive/answer/6374270).

## Data and recovery-key coverage

The current logical database export includes the Auth schema rows (including user identities/password hashes as held by Auth), application tables, role names/memberships without role passwords, catalog/RLS/grant/migration evidence, and Storage object metadata. Supabase confirms database backups contain Storage metadata but not the object bodies. The current local script aborts for any nonzero `storage.objects` count; that must remain until a separately approved least-privilege body-export path exists. Direct SQL against the Storage schema is not an object download mechanism and Supabase says object operations must go through the Storage API. Do not use a service-role key for this job: it bypasses Storage RLS and has broad privileges. See [Supabase backup coverage](https://supabase.com/docs/guides/platform/backups), [Storage RLS](https://supabase.com/docs/guides/storage/security/access-control), and [Storage schema limits](https://supabase.com/docs/guides/storage/schema/design).

To include private object bodies at no added service cost, the owner would have to separately approve and review a dedicated read-only Storage API identity and the narrowly scoped RLS `SELECT` policy needed to list/download the required private buckets. That is a production Auth/policy change and is not authorized here. If the current policies cannot provide read-only full inventory/content access, there is no approved safe zero-cost route to complete Storage recovery; stop the cycle until a reviewed solution is approved.

The encrypted age recovery identity and its passphrase stay separate in the existing approved secure vault. The uploader uses only the public age recipient to wrap per-backup data keys. Neither secret belongs in Drive, source, config, logs, or the package. The isolated verifier needs an approved way to obtain the private identity/passphrase for restore; do not cache them beside the backup or in the uploader account. Existing local DPAPI material is bound to the Windows identity and is not a portable recovery method. A cross-device portable restore still requires separately conveyed recovery material and the masked passphrase.

Auth database rows alone do not reproduce every Supabase Auth project setting. Recovery evidence must include a sanitized, non-secret inventory of Auth providers, redirect URLs, email/SMS behavior and other relevant project settings, plus a tested recreation procedure. Never export provider secrets into the backup package.
